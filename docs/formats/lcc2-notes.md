# LCC2 (XGRIDS), format notes (M3.1)

Research notes for XGRIDS' `.lcc2` format, from the local `Dehaar` capture
(`assets/Dehaar/`, gitignored, **not redistributable**) cross-checked
against the [LCC whitepaper](https://github.com/xgrids/LCCWhitepaper).
Read together with [`streamed-sog-notes.md`](streamed-sog-notes.md) (Streamed SOG) and
`ROADMAP.md` M3.

## Directory layout

```
Dehaar/
├── De haar.lcc2 ← manifest (JSON, ~300 KB)
├── data/
│ ├── 3dgs/*.sog ← splat tiles (standard SOG v2 bundles) + env.sog
│ ├── mesh/*.ply ← collision/nav meshes (loaded; see "Collision meshes")
│ └── mesh/*.btree ← XGRIDS' own BVHs over those meshes (skip, see below)
└── info/ ← poses.json, report.json, thumb.jpg (skip)
```

**The splat tiles are plain SOG v2** (verified: `version: 2`, no `shN`),
decodable by our existing `parseSog`. One `.sog` file packs *several*
nodes' splats concatenated: e.g. `0_9_0.sog` holds 524,407 splats, and one
node reads the sub-range `[0, 43866)` of it. This is exactly the Streamed
SOG chunk model, a file is a chunk, a node's `(start, count)` is a range
within it.

## Manifest schema (`De haar.lcc2`, version "0.0.2")

```jsonc
{
 "version": "0.0.2",
 "source": "lcc", "dataType": "PortalCam", "fileType": "portable",
 "offset": [0,0,0], "shift": [0,0,0], "scale": [1,1,1], // identity here
 "totalSplats": 16759489,
 "totalLevels": 6,
 "lodSplats": [8543271, 4255358, 2120977, 1055507, 524407, 259969],
 "root": Node
}

interface Node {
 id: string; // tree path, e.g. "0_7_0_1_3_0"
 boundingBox: { min: [x,y,z]; max: [x,y,z] };
 childNum: number;
 child: Record<string, Node>; // keys "0".."childNum-1"
 data?: {
 "3dgs"?: { name: number; start: number; count: number }; // splat range
 mesh?: { name: number; vertex: number; face: number }; // collision tile
 bvh?: { name: number; ... }; // skip
 env?: { name: number }; // root only
 };
 // root also carries the global file lists:
 splatFiles?: string[]; // 32 entries; `name` indexes into this
 meshFiles?: string[]; // 24 entries; `data.mesh.name` indexes into this
 bvhFiles?: string[]; // 24 entries; skip
}
```

- `data["3dgs"].name` indexes `root.splatFiles`; `start`/`count` are the
  splat sub-range within that decoded tile.
- `root.data.env.name` → `splatFiles[31]` = `env.sog` (29,366 splats), the
  always-present environment/background.
- `offset`/`shift`/`scale` are a global similarity transform on positions.
  All identity in `Dehaar`; SOG decode already yields world positions, so
  we apply them only if non-identity (a mesh transform suffices).

## Environment tile (`root.data.env`): M12

An `.lcc2` capture carries one **always-on environment/background** tile: the
sky and distant surround that has no LOD ladder and is not part of the octree
cut. The root node names it in `root.data.env.name`, an index into
`root.splatFiles` (`splatFiles[31]` = `env.sog` in `Dehaar`). It is a plain
SOG v2 bundle like every other tile, decodable by `parseSog`.

**The manifest never states its splat count.** Unlike a `3dgs` range
(`{name, start, count}`), `env` carries only `{name}`, no `start` (it is the
whole file, offset 0) and no `count`. So the count is **measured when the tile
decodes** (`SplatData.count`); `Dehaar`'s `env.sog` holds **29,366** splats.
`StreamedSplatMesh.environmentSplatCount` reports it once loaded (0 before).

How VLAM! loads it (`buildLcc2Scene` → `StreamedScene.environment`, applied by
`StreamedSplatMesh`):

- The env file is **pinned** so an LOD reschedule never cancels its fetch.
- It loads **once**, on the first update after it is wanted, and is appended
 **whole** as a single resident pool range, never scheduled by camera
 distance, never evicted, never refetched.
- It sits **outside the LOD budget**, drawing from the pool's capacity
 headroom (the ~1.5× slack over the resident ceiling), so enabling it does
 not steal detail from the LOD cut.
- `StreamedSplatMesh.setEnvironmentEnabled(boolean)` shows/hides it live by
 flipping the pool range's active flag, instant, no refetch. Start hidden
 with the `environmentEnabled: false` load option (the demo's `?env=0`; press
  `v` to toggle). `hasEnvironment` reports whether the scene ships one.

## Collision meshes (`data/mesh/*.ply`)

An `.lcc2` capture ships plain triangle meshes beside its splats, the
walkable/solid geometry, for hosts that want collision or spatial queries.
`parseMeshPly` reads them and `StreamedSplatMesh.loadCollisionMeshes()`
fetches the set; vlam builds nothing on top (see `ROADMAP.md` M9's scope
guard). Verified against `Dehaar`:

- **24 tiles**, 24 nodes carrying `data.mesh`, 24 distinct `name`s, one
 tile per mesh-bearing node, no sharing in practice (the loader dedupes by
  `name` anyway, since nothing in the schema forbids it).
- Header is uniform: `binary_little_endian 1.0`, `comment generated by
  meshSplit`, `element vertex N` (**float x/y/z only**, no normals or
  colors), `element face M` (`property list uchar int vertex_indices`).
  Plain triangle soup; the largest tile is 53,260 verts / 74,790 faces.
- **Same source-local Z-up frame as the splats**, so a tile needs the same
  `createLcc2ToThreeMatrix()` correction. Confirmed empirically: with the
 transform applied the collision spans y −5.2…23.6 m (a plausible building
 height) inside the splats' y −27…55 m, and a floor probe finds ground at
 y ≈ −0.4 with roof hits at 4–6.7 m. Untransformed it would span a
 horizontal extent instead.
- **Collision covers far less ground than the splats**: 122 × 29 × 99 m of
 castle and grounds inside a 400 × 82 × 418 m capture. Probes outside it
 legitimately find nothing, so "no floor here" is a normal answer, not a
 failure. (De Haar's moat reads as a hole for the same reason.)
- `bvhFiles` / `data.bvh` point at `.btree` companions: XGRIDS' own BVH,
 32-byte records that look like a 6-float AABB plus two uint32s, but the
 format is undocumented and unverified. We skip them and build our own
 acceleration structure from the triangles instead.

## LOD model, a **cut-based octree** (verified from the data)

This is the important finding and it differs from Streamed SOG.

- **`level = totalLevels − depth`.** Root is depth 0 (env only). Depth 1 =
 coarsest (level 5), depth 6 = finest (level 0). Confirmed: the node
 counts at each depth sum *exactly* to `lodSplats[level]`
 (depth 6 → 8,543,271 = `lodSplats[0]`; depth 1 → 259,969 = `lodSplats[5]`).
- **Each level fully tiles the whole scene.** Because per-depth sums equal
  `lodSplats`, rendering the entire scene at a uniform level ℓ means drawing
  exactly the depth-(6−ℓ) nodes, a *complete* representation. The finest
  render is 8.5M splats **alone**, not 16.76M, so coarser nodes are
  **replaced** by finer ones, not blended on top. It is a **cut**
  (antichain) through the octree, not an additive hierarchy. (The
  whitepaper's "hierarchical LOD" wording is about the tree shape, not
  additive blending; `totalSplats` = 16.76M is the on-disk sum of all
  levels, never drawn at once.)
- The tree interleaves two edge kinds:
  - **Refinement** (`childNum == 1`): same bounding box, ~2× the splats
    (21k→43k→89k→177k down one chain), a finer LOD of the *same* region.
  - **Subdivision** (`childNum > 1`): the bounding box splits into
    spatially disjoint children.
- Nodes per depth in `Dehaar`: `{1:11, 2:11, 3:21, 4:31, 5:47, 6:72}` (194
  nodes incl. root). A single tile file backs many nodes (file 0 → 11
  nodes, file 2 → 14, …) at different `start` offsets.

## Why this is NOT a drop-in for the flat `LodScheduler`

Our Streamed SOG `LodScheduler` picks a level **per leaf independently**,
which assumes each leaf's per-level ranges cover **only that leaf's
region** (spatially disjoint at every level). LCC2 coarse nodes are
**shared ancestors** covering many finest cells. If two sibling cells
disagree, one selects its fine node, the other selects a shared coarse
ancestor that spatially overlaps the first, the first cell's region is
drawn twice (fine + coarse) → double-brightness overdraw. Independent
per-leaf selection cannot guarantee the cut property; the selection must be
**cut-based** (descend or stop per node, exactly one node per root→leaf
path).

## Implemented approach (reuse the M2 machinery)

`StreamedSplatMesh`'s apply loop, chunk cache, region-atomic swaps,
coarse substitution, retry/backoff, budget-by-desired-set, WebGL2 sort, is
**format-agnostic**: it consumes `LodRun[]` (a `{file, offset, count}` plus
a leaf interval) each frame and diffs against resident runs. Reuse it by:

1. **Order the finest cells** (deepest nodes) 0..K−1 in tree-DFS order.
 Each node gets a **leaf interval** `[minCell, maxCell]` over its subtree.
 Ancestor intervals nest over descendants → the existing
 overlap-based swap grouping treats an ancestor↔children swap as one
 atomic group (spatial overlap = interval overlap). No double-draw,
 because a valid cut never has an ancestor and descendant both active.
2. **Cut selection** (new `OctreeLodSource`): traverse from the root's
 children (the coarsest full cover); greedily descend the
 highest-priority nodes (nearest, in-frustum, per distance-to-AABB with
 hysteresis) until the splat budget is spent. Out-of-frustum nodes stay
 shallow (distance penalty, as in the SOG scheduler). Emit each selected
 node as a run `{file: name, offset: start, count, leaf interval}`.
   `env.sog` is always resident (a pinned run).
3. **Abstract the scheduler** behind a small interface both
   `LodScheduler` (SOG) and `OctreeLodSource` (LCC2) implement
 (`computeDesiredRuns`, `coarsestRunsFor`, `budget`, `lodBaseDistance`);
   `StreamedSplatMesh.load` picks the source by extension (`.lcc2` vs a
   Streamed SOG `lod-meta.json`). The chunk-file list, scene bounds and
   pinned (coarsest) files come from a shared manifest struct.

## Coordinate frame

XGRIDS LCC2 is Z-up. VLAM! normalizes `.lcc2` meshes at load time to the
same Three.js Y-up frame used by the XGRIDS LCC and Spark viewers with the map
`(x, y, z) → (-x, z, y)`. Bounds and LOD data remain source-local;
`matrixWorld` and `worldToLocal` account for the mesh transform. Host apps
must not apply another LCC2 rotation. PLY / SOG remain Y-down and still need
the usual 180° X flip in the host.

## Licensing

The LCC whitepaper grants a **non-exclusive, royalty-free** license to
implement third-party readers, with attribution and a "derivative formats
must be published under terms no less open" clause, plus a restriction
against using the format to train AI that competes with XGRIDS; governed by
PRC law. Implications for us:

- Implementing an original **reader** over the openly published spec is
  permitted. Our adapter code is original (no XGRIDS code copied).

  gitignored; never commit it, and keep it out of any published demo.
